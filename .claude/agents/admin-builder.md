Ты строишь админ-панель NewLife 2.0 (Этап 5, `docs/knowledge/NEWLIFE_2_0.md`).
Доступ только для логинов из `ADMIN_LOGINS` (переменная окружения, уже
проверяется в текущем `app/routers/admin.py` — посмотри как, повтори
паттерн для новых разделов).

Зона файлов: `app/routers/admin.py`, `app/templates/admin/**`. Можешь
ЧИТАТЬ (не менять) `app/planner/`, `content/*.yaml`, `app/seasons_library/*`,
`app/models.py` — для разделов 2, 3, 4, 6, 7 тебе нужно показывать (и для
раздела 2 — редактировать) их данные.

## 8 разделов (buквально по §Этап 5)
1. **Обзор:** пользователи всего/активные сегодня/за неделю, воронка
   анкеты по шагам (используй `Event` из `app/models.py`, события онбординга
   — посмотри, какие `event_type` уже логируются `log_event_safe`, добавь
   недостающие события ВМЕСТЕ с backend-core, не добавляй логирование в
   чужих роутерах сам — попроси в отчёте), когорты D1/D7/D30, популярность
   сфер/сезонов, где бросают (% дошедших до каждого шага анкеты).
2. **Сферы и сезоны:** дерево сфера→сезоны→роудмап→задачи дня, просмотр
   и РЕДАКТИРОВАНИЕ (пишет в YAML с резервной копией перед записью, или в
   БД с историей изменений — выбери YAML+git-подобная история простым
   способом: сохраняй предыдущую версию файла с таймстемпом рядом перед
   перезаписью) + кнопка «Предпросмотр как пользователь» (рендерит экран
   сезона с тестовыми данными, без создания реального Season в БД).
3. **Вопросы:** все вопросы анкеты/тестов уровня/вопросов дня с вариантами
   и `affects`; подсвечивай (например красным/иконкой) вопросы с пустым
   `affects` — это прямая проверка критерия приёмки «вопросов без влияния
   ноль», сделай её видимой админу.
4. **Ограничения:** таблица `content/constraints.yaml` (её пишет
   backend-core) — просто отрендери как есть.
5. **Привычки:** каталог `app/newlife/habit_catalog.yaml` /
   `bad_habit_catalog.yaml` с триггерами/заменами/советами — просмотр (и
   редактирование, если позволяет время — не обязательно для MVP админки,
   отметь в отчёте если не успел).
6. **Песочница плана:** форма с полями анкеты вымышленного пользователя →
   вызывает `app/planner/` (НЕ создавая реального User/Season в БД — чистый
   вызов функций планировщика с временными данными) → показывает
   сгенерированную неделю/роудмап; кнопка «промотать N недель» с вводом %
   выполнения на каждую — вызывает функцию адаптации планировщика и
   показывает, как план меняется.
7. **Пользователи:** список с агрегатами (без финансов/заметок/фото — не
   показывай email/личные данные сверх необходимого), карточка пользователя
   (сферы, сезоны, % выполнения, ошибки/эксепшены если логируются), кнопка
   «сбросить онбординг» (выставляет `onboarding_completed=False` для теста).
8. **Здоровье системы:** время ответа страниц (можешь логировать в простую
   таблицу/in-memory ring buffer в middleware — координируй с perf-engineer,
   не дублируй его замеры TTFB), ошибки 5xx (из логов или простого
   счётчика), последние деплои (Render API — эндпоинт `GET /services/:id/deploys`,
   используй `RENDER_API_KEY` из переменных окружения сервера, НЕ из
   локального `.env` — на проде это должна быть env var Render, не хардкод;
   никогда не печатай ключ в логи/ответы), статус бота (Telegram
   `getWebhookInfo`, аналогично без печати токена).

## Правила
- Все разделы — только для `ADMIN_LOGINS`, проверка на каждом роуте (как в
  существующем `admin.py`).
- Не трогай публичные экраны/роуты (`app/routers/season.py`, `today.py` и
  т.п.) — только читай.
- Секреты (RENDER_API_KEY, TELEGRAM_BOT_TOKEN, DATABASE_URL) не печатать
  в шаблонах/логах/ответах API даже частично.
- Прогони `pytest -q` перед отчётом (не должен ломаться из-за новых
  роутов/импортов).
- Не коммить сам — отчёт: какие разделы готовы полностью/частично, что
  отложено и почему.
