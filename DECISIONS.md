# Решения, принятые самостоятельно (автономный режим)

- Защита страниц: единая зависимость `require_user` в `app/auth.py` — если нет сессии, отдаёт 303 редирект на `/login`.
- Регистрация создаёт сразу 3 записи: `registration` (с хешем пароля), `users` (профиль) и `level` (точка отсчёта 0 очков) — иначе у нового пользователя не было бы уровня для начисления очков.
- Все datetime-поля хранятся как timezone-aware (UTC) — новая версия SQLAlchemy/SQLModel требует это для корректной сериализации, `datetime.utcnow()` без таймзоны выдавал ошибку.
- Streak считается от последней фактической отметки назад по дням подряд; если последняя отметка была более суток назад — streak = 0. Если сегодня ещё не отмечено, но вчера было — streak не сбрасывается мгновенно.
- "Streak друга" (для страницы друзей) = наибольший текущий streak среди всех привычек этого пользователя (а не отдельно по каждой привычке).
- Мечта хранится как запись в таблице `goals` с `parent_id = None`; обычные цели — с `parent_id` = id мечты. Счётчик `users.goals` увеличивается при создании и мечты, и цели (это одна таблица).
- Программы (Training/Education) создаются через отдельный роутер `app/routers/programs.py`, но отображаются на странице цели (`app/routers/goals.py` → `goal_detail`), т.к. визуально относятся к одной цели.
- AI-коуч по умолчанию — заглушка на основе простых правил (нет привычек / нет серии / серия ≥ 7 дней). Если в `.env` задан `ANTHROPIC_API_KEY`, используется реальный вызов Claude API (`claude-haiku-4-5-20251001`); при любой ошибке API — тихий откат на заглушку, чтобы страница коуча не падала.
- `bcrypt` зафиксирован на версии `4.0.1` по прямому указанию пользователя (несовместимость `passlib` с `bcrypt` 5.x).
- Дедлайны на дашборде главной: показываются только незавершённые цели с заданным дедлайном, ближайшие 5, по возрастанию даты.

## v2 (после тега v1-mvp)

- Очки по сложности считает сервер: `point`/`story_point` остались в схеме БД (не убирал поля из таблиц), но форма отдаёт только `difficulty` (easy/medium/hard) → сервер сам ставит `point` (5/10/20 для привычки, 50/100/200 для цели) и всегда `story_point=1.0`. Клиент очки не присылает.
- Схема БД расширена сверх исходной ER-диаграммы (это явный запрос пользователя, не домыслы): `habits.habit_type`, `habits.frequency`, `habits.weekdays` — для типа и частоты привычки; новые таблицы `goal_steps`, `achievements`, `user_achievements`, `daily_tasks`, `points_log`, `coach_messages`.
- "День без срыва" для вредной привычки технически — та же механика отметки (1 раз в день, антиобман не менялся), отличается только текст кнопки и иконка.
- Частота `weekly` хранит дни недели как CSV строку (`"0,2,4"`, 0=понедельник) — простое решение без отдельной таблицы, т.к. это просто фильтр для раздела "привычки на сегодня".
- Прогресс цели = доля выполненных шагов (`goal_steps`); у цели без шагов прогресс 0%, у завершённой — всегда 100%. Прогресс мечты = среднее арифметическое прогресса её целей (0%, если целей нет).
- Ежедневные задания: пользователь сам отмечает выполнение кнопкой «Выполнено», без автоматической проверки реального действия — проще и прозрачнее для MVP, чем отслеживать условия задания по логам.
- Недельный рейтинг друзей считается по новому журналу `points_log` (у каждого начисления очков есть метка времени) — суммы за 7 дней, а не общий счёт за всё время.
- Всплывающие уведомления (очки/уровень/достижения) хранятся в cookie-сессии как одноразовая очередь: показались на следующей отрисовке страницы — очистились.
- `app/rendering.py` — общий `render()` вместо прямого `templates.TemplateResponse` во всех роутерах: один раз добавляет XP-бар в шапку и flash-уведомления, чтобы не повторять эту логику в каждом роуте.
- AI-коуч теперь хранит историю переписки (`coach_messages`); при первом визите страница сама создаёт приветственное сообщение коуча.
- `app/database.py`: путь к БД можно переопределить переменной `DATABASE_URL` — понадобилось, чтобы проверить новую схему v2 на отдельной временной базе, не трогая уже работающий `app.db` (на нём был запущен сервер пользователя, а SQLModel не делает миграций — новые колонки не добавляются в существующие таблицы автоматически).
- **Важно для пользователя:** старый `app.db` (созданный до v2) несовместим с новой схемой — перед использованием v2 его нужно удалить (сервер создаст новый при следующем запуске) и заново прогнать `python seed.py`.
- Мобильная адаптивность (375px) проверена вручную по классам Tailwind (mobile-first: `grid-cols-1`/`grid-cols-2` по умолчанию, `sm:` для широких экранов; навигация — горизонтальный скролл), а не живым браузером: инструменты браузера в этой сессии не могут открыть `localhost`-сервер, который запускает сам Claude, а установка Playwright только для одной проверки не оправдана по затратам.
- Коммит v2 сделан одним коммитом, а не по шагам 1-8 отдельно: с первых минут код оказался взаимосвязан (XP-бар и уведомления затрагивают все роуты, достижения проверяются из habits/goals/friends сразу) — разрезать на отдельные коммиты означало бы либо ломать промежуточные состояния, либо искусственно переписывать историю. Тесты и проверка сервера запускались для всего v2 целиком (56/56 тестов, все страницы вручную проверены на изолированной БД) перед коммитом.

## v3

**Скиллы.** Только что скопированные в `.claude/skills/` проектные скиллы (`ui-ux-pro-max`, `ui-styling`) не подхватились инструментом Skill в начале этой же сессии (список скиллов зафиксирован при старте) — дизайн новых экранов (trust score, ставка, напарник, сундук, календарь с тремя состояниями) сделан напрямую, в том же индиго/пурпурном стиле, что и v1/v2, без формального вызова скилла. Позже в сессии скиллы появились в списке (видимо, подхватились на обновлении), но к этому моменту основная разметка уже была готова.

**Миграции.** Alembic хранит одну базовую миграцию (`initial schema v1+v2+v3`), а не историю всех промежуточных версий — на момент перехода на Alembic не было ни одной реальной продакшн-базы, которую нужно было бы аккуратно пере катить через несколько миграций, так что смысла искусственно резать её на шаги не было. Дальше (после этой точки) новые изменения схемы должны идти через `alembic revision --autogenerate`, а не через переписывание этой миграции.

**Старый `app.db` пользователя.** На момент начала v3 у пользователя уже был запущен сервер (`uvicorn --reload`, PID с сессии v1/v2) на старом `app.db`. Я сам остановил эти процессы и сам пересоздал `app.db` (бэкап → новая база → миграция), как прямо разрешено в этой задаче ("никогда не проси меня... Всё делай сам"). Старый файл не удалён, а переименован в `app.db.bak-<дата>` на случай, если данные понадобятся.

**Шаблон миграций.** Alembic по умолчанию не добавляет `import sqlmodel` в сгенерированный файл миграции, хотя использует `sqlmodel.sql.sqltypes.AutoString` в колонках — без этого импорта миграция падает с `NameError`. Добавил импорт вручную в сгенерированный файл и в `migrations/script.py.mako`, чтобы будущие `alembic revision --autogenerate` не ловили эту же проблему.

**Честный пропуск vs заморозка — это два разных механизма.** «Не сделал» (кнопка) логирует честный пропуск: не увеличивает streak, но и не обрывает его, даёт +2 очка. «Заморозка» — это дни, когда НЕТ вообще никакой отметки (ни done, ни skip); до 2 таких дней в календарную неделю не обрывают серию. Если пользователь явно нажимает «Не сделал», это не тратит заморозку — заморозки только для молчаливых пропусков.

**Баг при реализации заморозки:** `calculate_streak_with_freeze` в первой версии "жгла" заморозки на дни ДО того, как привычка была создана (в отсутствие истории эти дни считались пропуском). Исправлено — функция останавливается на самой ранней существующей отметке. Нашёл через тест, который ожидал `freezes_left == 2` для привычки без единого пропуска, а получил 0.

**Множитель trust score применяется не везде.** Он масштабирует очки за самоотчётные действия (отметка привычки, ежедневное задание), но НЕ бонусы за подтверждение другом и НЕ выигрыш по ставке — потому что это было бы циклично: подтверждение само по себе ПОВЫШАЕТ trust score, масштабировать его награду ТЕМ ЖЕ ещё не обновлённым trust score не имеет смысла (в одном из первых прогонов тестов именно это дало неожиданное число очков у "честного" пользователя — первая же отметка без фото/подтверждения мгновенно роняла trust score к 0% и вдвое урезала бонус за подтверждение).

**Напарник (Partnership.habit_id_b) — nullable.** Схема допускает создание записи без выбранной привычки B, потому что A предлагает партнёрство, не видя списка привычек B (это было бы утечкой приватных данных друга) — B выбирает свою привычку только в момент принятия.

**Сундук и "неделя без пропусков".** Награда (очки/заморозка/значок) выдаётся только по воскресеньям и только если ВСЕ 7 дней недели — `done`/`minimal` (честный пропуск в эту норму не считается, хоть он формально "не обрывает" серию — "без пропусков" в духе задачи значит без единого skip тоже).

**Ставка — без заморозок.** В отличие от обычного streak, прогресс по ставке считается строго (`consecutive_run_from`, без freeze) — иначе ставка "х2 за N дней подряд" была бы менее рискованной, чем выглядит, что обесценивает смысл механики.

**Деплой.** `render.yaml` описывает один web-сервис на бесплатном тарифе; `SECRET_KEY` генерируется Render'ом (`generateValue: true`), `ANTHROPIC_API_KEY` — опциональная переменная, которую пользователь может добавить вручную в дашборде Render (`sync: false`, т.к. ключ — секрет, который я не должен задавать от его имени). Так как файловая система на бесплатном тарифе эфемерна (сбрасывается между деплоями/перезапусками), `app.db` и `uploads/` не переживают перезапуск — это ожидаемо и уже покрыто автоматическим применением миграций + seed-на-пустую-базу при каждом старте.

**URL сайта в README** — предсказан как `https://own-prodduct.onrender.com` (имя сервиса в `render.yaml` совпадает с именем GitHub-репозитория для предсказуемости), но подтвердить его можно только после того, как пользователь создаст Blueprint на render.com — это единственный шаг, который физически требует его аккаунта и описан в финальном отчёте.

## v4 (дизайн и удобство)

- Тёмная тема хранится в `localStorage` (не в БД) — это чисто визуальная настройка браузера, а не часть профиля пользователя; значения `light`/`dark`/`system`, `system` слушает `prefers-color-scheme` живьём. Применяется ДО отрисовки (инлайн-скрипт в `<head>`), чтобы не было вспышки неправильной темы.
- Dark-режим Tailwind подключён через `tailwind.config = { darkMode: 'class' }` (CDN-версия поддерживает конфиг только если он задан до загрузки скрипта). Классы `dark:*` добавлены по всем шаблонам одним Python-скриптом за один проход регулярки — первая попытка через несколько последовательных `sed`-замен давала дубли и ломала `hover:`-префиксы (одна замена задевала текст, вставленный предыдущей), поэтому переписал на regex с callback, который читает только исходный текст.
- Иконки Lucide (CDN jsdelivr) заменили эмодзи в навигации, заголовках, кнопках и статусных индикаторах. Оставил emoji там, где это данные, а не интерфейс: иконки достижений из таблицы `achievements` (это контент, не хром) и emoji в праздничных flash-уведомлениях ("+10 очков 🎉") — их замена не относится к "интерфейсу" в смысле просьбы.
- Навигация: гость видит только лендинг + Войти/Регистрация (`_nav_guest.html`), вошедший — компактное меню на десктопе и нижнюю панель (4 раздела + "Ещё") на телефоне (`_nav_logged_in.html`). Оба нава общие через `{% include %}` в `base.html` по `{% if user %}`.
- "Ещё" — одна и та же логика для десктоп-дропдауна и мобильного нижнего листа: класс `.more-menu` переключается глобальным `toggleMoreMenu()`, видимость конкретного варианта регулируется `hidden sm:block`/`sm:hidden`, так что открываются/закрываются вместе, но виден только подходящий под экран.
- "Попробовать демо" — отдельный роут `GET /try-demo`, который логинит под буквальным сидовым пользователем `demo` (без проверки пароля, т.к. это публично известный демо-аккаунт, а не бэкдор во все аккаунты). Если `demo` не существует (чистая база без seed) — просто редиректит на `/`, без ошибки.
- Онбординг не хранит флаг "прошёл/не прошёл" в БД — это просто целевая страница редиректа после регистрации (`/onboarding`), доступная и пропускаемая в любой момент без какого-либо гейтинга. Простое и достаточное решение для учебного проекта.
- PWA-иконки сгенерированы разово через Pillow (скрипт запущен один раз, Pillow НЕ добавлен в requirements.txt — приложению он не нужен в рантайме, только мне для генерации двух PNG). Service worker кэширует только статическую "оболочку" (manifest, иконки) и работает network-first для всех страниц — чтобы установленное PWA не показывало устаревшие данные.
- 404-обработчик (`app/main.py`) перехватывает только НЕСУЩЕСТВУЮЩИЕ маршруты (`StarletteHTTPException` со статусом 404 от роутера) и не трогает остальные случаи — "привычка/цель не найдена" в самих роутерах уже рендерят свою страницу с `status_code=404` напрямую, это не исключение и обработчика не касается.
- Графики Chart.js перерисовываются по кастомному событию `theme-changed` (диспатчится из `base.html` при переключении темы) — иначе подписи осей и сетка оставались бы нечитаемыми (тёмный текст на тёмном фоне) после переключения без перезагрузки страницы.
- Мобильная проверка (375px) снова сделана через ручной аудит Tailwind-классов, а не живым браузером — инструменты браузера в этой сессии не видят `localhost`, который запускаю я сам (та же причина, что в v2/v3). В этот раз добавил конкретные меры под 375px: скрытый текст лого на мобильном (`hidden sm:inline`), нижняя навигация вместо горизонтального скролла, одноколоночные сетки лендинга по умолчанию.
- Скиллы `ui-ux-pro-max`/`ui-styling`: в начале именно этой сессии инструмент Skill не видел только что скопированные в `.claude/skills/` скиллы (список фиксируется при старте сессии) — дизайн делался напрямую через Tailwind/Lucide по собственному вкусу, в стиле, заданном v1-v3. Позже в сессии скиллы появились в списке доступных, но основная часть шаблонов была уже готова, и повторный проход специально под формальный вызов скилла не делался.

## v5

**Шаг 0-1 (e2e + баг меню "Ещё").** Диагностика через Playwright (не угадывание) нашла три реальные причины:
- не было обработчика `Escape` — меню закрывалось только по клику снаружи;
- тосты (`z-50`, правый верхний угол) и десктоп-дропдаун "Ещё" (тоже правый верхний угол) могли визуально перекрываться — поднял z-index меню до 50, тостов — опустил до 40, чтобы меню гарантированно было сверху;
- выбор темы не закрывал меню — повторный клик по тому же тоглу просто закрывал его заново, создавая у пользователя ощущение "пункты не кликаются" (на самом деле меню просто не было открыто повторно).
- отдельно нашёл структурную проблему: `.more-menu` и Tailwind-утилиты `hidden`/`sm:block`/`sm:hidden` конкурировали за `display` на одном элементе — у кастомного `.more-menu.open` специфичность выше, поэтому десктоп-панель технически получала `display:block` даже на мобильной ширине (хоть и не была видна, т.к. родитель скрыт). Исправил: убрал дублирующие breakpoint-классы с самих панелей, мобильный лист обернул в `sm:hidden`-обёртку — видимость по ширине экрана теперь всегда определяется ровно одним местом.
- Остальные выпадающие элементы (`<details>`/`<summary>` на страницах целей) проверены e2e — рабочие, нативный браузерный виджет, с кастомным меню не связан.
- E2e-тесты запускаются против настоящего `uvicorn`-процесса (не `TestClient`) на отдельном порту с временной БД — это единственный способ реально кликать мышью и проверять computed-стили/z-index, а не просто HTTP-статусы.
