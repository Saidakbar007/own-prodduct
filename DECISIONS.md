# v6a — решения по неоднозначным местам задания

Этот файл фиксирует интерпретации, которые пришлось выбрать самостоятельно,
когда формулировка задания допускала больше одного разумного варианта.

## 1. Уровни и ранги

- XP до следующего уровня L→L+1: `80 + 20*L` (L — текущий уровень, считая с 1).
  Суммарный XP для достижения уровня N = сумма этой формулы по L=1..N-1.
  Уровень не хранится отдельным полем — считается "на лету" из `Level.point`
  (общий накопленный XP, то же поле что и раньше), так что никакой реальной
  миграции данных не нужно: старые очки автоматически попадают в новую шкалу.
  "Миграция" из задания реализована как пересчёт `Level.name` (хранит название
  ранга) под новую систему рангов-по-уровню вместо старой системы
  рангов-по-очкам — выполняется разово в миграции Alembic для всех
  существующих пользователей.
- Старые 5 названий порогов ("Новичок/Ученик/Практик/Мастер/Легенда")
  совпадают по именам с новыми 5 рангами — только границы теперь считаются
  по номеру уровня (1-5/6-15/16-25/26-40/41-50), а не по сумме очков.
- Выше уровня 50 (и ранга «Легенда») XP продолжает копиться в `Level.point`
  (не теряется, future-proof), но уровень в UI показывается максимумом — 50.

## 2. Личности (5 персон)

- Уровень личности = уровень её сферы (как и раньше, 1-20, `sphere_level()`).
- Стадия личности 1-5 по уровню: 1-3→1, 4-7→2, 8-11→3, 12-15→4, 16-20→5.
- Стадия героя = номер ранга героя (1-5), как и сказано в задании буквально.
- Ведущая личность = сфера с наибольшим XP (сумма `PointsLog.points` с этим
  `sphere`) за последние 14 дней; при равенстве — порядок как в `SPHERES`
  (сила → интеллект → дисциплина → здоровье → харизма).
- Титул "<Личность> · <Ранг>" — Ранг здесь это РАНГ ГЕРОЯ (общий), не что-то
  отдельное для личности (у личностей нет своего "ранга", только "стадия").
- Состояния по дням с последней активности в сфере (последний `PointsLog`
  с этим `sphere`, либо «никогда» = трактуется как «спит»):
  - `≤ 3 дня` → активна
  - `4-20 дней` → дремлет (число "7+" в задании — ориентир внутри этого
    диапазона, а не точная граница; точные границы 3 и 21 даны явно и должны
    разбивать все дни без пропусков, поэтому дремлет = всё между ними)
  - `≥ 21 день` → спит
- "Пробуждение" (+50% XP за первую отметку после сна) применяется к XP ЭТОЙ
  конкретной отметки — и к общему XP, и к XP сферы (они начисляются одним
  событием из одного и того же `base_points`). У личности, которая НИКОГДА
  не была активна, бонуса нет — это старт, а не пробуждение (иначе бонус
  срабатывал бы на самой первой отметке у вообще всех пользователей).
- "Гармония" (все 5 личностей активны за последние 7 дней, т.е. у каждой из
  5 сфер была хоть одна отметка за неделю):
  - +10% к монетам — применяется как множитель в момент начисления монет
    (`award_coins`), проверяется живым запросом, не хранится флагом;
  - "сундук на ступень выше" — реализовано как повышение случайной награды
    сундука на одну ступень по шкале `badge < freeze < points` (если выпали
    очки — берётся следующий по величине тир очков, а не случайный).

## 3. Голоса коуча персон

- Реализованы 4 типа триггеров (буквально из задания, без лишних добавок):
  - приветствие — от ВЕДУЩЕЙ личности, один раз в календарный день, при
    заходе на `/hero` (проверяется по последнему `CoachMessage` с этим
    `persona_code` за сегодня — если уже было, не дублируем);
  - пропуск (`kind="skip"` при отметке) — от личности сферы привычки,
    отдельным flash-сообщением вдобавок к существующему "Честно признано";
  - серия — от личности сферы привычки, при достижении серии 3/7/14/30/60/100
    дней (а не на каждую отметку — иначе было бы слишком навязчиво);
  - предупреждение о балансе ("Бард спит уже N дней") — показывается прямо
    в карточке личности на `/hero` для каждой личности в состоянии "спит"
    (не как push-уведомление, чтобы не плодить лишние тосты на каждой
    странице — баланс личностей и так виден на специальной странице).
- У каждой личности ≥10 шаблонов на каждый тип триггера, подобранных под
  характер (см. `app/services/persona_voices.py`).
- При наличии `ANTHROPIC_API_KEY` генерируется реплика через Claude с
  системным промптом персонажа; при ошибке или отсутствии ключа — заглушка
  из шаблонов (тот же паттерн отказоустойчивости, что уже используется в
  `app/services/coach.py` и `app/services/difficulty.py`).

## 4. Монеты

- Начисление монет добавлено в: отметку привычки (1/2/4 по сложности
  easy/medium/hard, определяется через `difficulty_from_points(habit.point)`),
  +1 монета если прикреплено фото, выполнение ежедневного задания (3 монеты
  за задание, +5 бонус когда выполнены все 3 за день), получение достижения.
- Тиры монет за достижения (разделены по "силе" достижения, так как в
  задании дано только "20/50/100" без привязки к конкретным кодам):
  `first_habit`, `first_friend` → 20; `streak_7`, `first_goal_done` → 50;
  `streak_30`, `checks_100` → 100.
- Множитель trust на монеты (отдельная функция от множителя XP, который был
  и раньше): `<40` → ×0.5, `40-79` → ×1.0, `80+` → ×1.2.
- За монеты нельзя купить XP/уровни/место в рейтинге — соблюдено
  конструктивно: в магазине нет таких товаров, а рейтinг друзей и так
  считается по % выполнения+streak (не по XP/монетам) ещё с v5.

## 5. Магазин и инвентарь

- Слот "заморозка серии" — отдельный расходуемый товар (не экипируется).
  Хранится как `User.freeze_stock` (0-2). Покупка (40 монет) не даёт
  мгновенного эффекта — она пополняет запас. Использование запасённой
  заморозки — явная кнопка на странице привычки на пропущенный день без
  ЛЮБОЙ отметки (не "честный пропуск" — тот и так не ломает серию
  бесплатно): превращает этот день в `HabitHistory(kind="skip")` и тратит
  1 из запаса. Это переиспользует уже существующую логику "skip не прерывает
  серию" вместо отдельной системы учёта по неделям.
- Цены (конкретные значения внутри данных диапазонов) заданы в
  `app/services/shop.py`, в каталоге по 12/12/10/5 товаров на слот.
- Легендарные предметы не продаются (`price=None` в каталоге) — их источник
  (ачивки/события) за рамками этого слайса, в каталоге они просто помечены
  "недоступно в магазине".

## 6. Заглушки картинок

- URL-пути из задания (`static/game/...`) — это путь на диске внутри
  `app/static/game/...`, отдаваемый существующим `/static`-маунтом, когда
  файл есть. Это и даёт "просто положить PNG с тем же именем — заработает"
  без единой правки кода.
- Если файла нет — шаблон использует `/game-placeholder/{category}/{name}`
  (отдельный роут, генерирующий SVG на лету: силуэт + подпись в цветах
  дизайн-токенов). Выбор между `/static/...` и `/game-placeholder/...`
  делает хелпер `game_asset_url()` по факту наличия файла на диске —
  шаблонам не нужно знать про эту разницу.

## 7. Сид

- У demo прокачаны разные сферы (разные уровни личностей), монеты получены
  "честно" (через реальные отметки/подтверждения, не вручную выставлены),
  куплены пара предметов в инвентаре. Одна персона (Бард/харизма) намеренно
  не трогается 25+ дней, чтобы попасть в состояние "спит" для демонстрации.

# v6b — решения по неоднозначным местам задания

## 8. Питомец

- Уровень героя 3 → появляется яйцо (поле `Pet.species = None`); до выбора
  вида питомец не существует как сущность — показывается карточка "яйцо".
- "Серия дней" для стадии питомца — лучший ТЕКУЩИЙ streak пользователя по
  всем привычкам (`best_streak_for_user`, уже существует) — питомец общий
  для героя, не привязан к одной привычке.
- Стадии 1-5 по серии: 0, 7, 30, 100, 365 дней — `PET_STAGE_BRACKETS`.
  Стадия НЕ откатывается: храним `Pet.best_stage_reached`, итоговая стадия =
  `max(текущая_по_streak, best_stage_reached)` — "не откатывается" буквально.
- "Грустит при пропуске" — настроение (`mood`), не стадия: если текущий
  streak == 0, а `best_stage_reached` >= 2 (уже был хотя бы раз на стадии
  "ур.7+") — питомцу "грустно", иначе "весело". Заморозка защищает
  автоматически: она не даёт streak обнулиться (это уже было верно в
  `calculate_streak_with_freeze`), значит грусть и так не наступит.

## 9. Сундуки — редкость и анимация

- Вероятности заменяют старый `random.choice(["points","points","freeze","badge"])`
  из v6a на явные веса 60/28/10/2% по той же шкале редкости, что и в
  магазине (`common/rare/epic/legendary` из `shop.py`) — переиспользуем её,
  а не вводим вторую отдельную "лестницу" тиров.
- trust ≥ 90 → шанс легендарного ×2 (4% вместо 2%); лишние 2% забираются у
  "обычного" (60% → 58%), остальные доли не трогаем — простейшая
  перенормировка без искажения относительных весов rare/epic.
- Награда по редкости: common → +20 XP, rare → +1 заморозка в запас
  (или +40 XP, если запас уже полный 2/2 — не терять награду впустую),
  epic → +80 XP + 10 монет, legendary → +150 XP + 30 монет + бейдж
  "Легендарная воля". "Заморозка" из сундука теперь пополняет тот же
  `User.freeze_stock`, что и покупка в магазине (единая экономика заморозок
  вместо параллельной системы `BonusFreeze` по неделям из v3).
- "Гармония" (+сундук на ступень выше) теперь поднимает именно по этой
  редкости (common→rare→epic→legendary), а не по старой лестнице
  badge/freeze/points — технически более правильная шкала для того же
  эффекта, описанного в v6a.
- Анимация открытия — чисто фронтенд: toast с `kind="chest"` получает CSS-
  класс `chest-rarity-{rarity}` и keyframe-анимацию (покачивание → вспышка
  цветом редкости → появление текста награды), без JS — достаточно для MVP.

## 10. Босс недели

- "Босс недели" — ОДИН общий босс на всех, определяется детерминированно
  номером ISO-недели (`iso_week % 6` по списку из 6 боссов) — а не который
  выбирает группа. Группы просто собираются сражаться с ЭТИМ боссом.
- Группа: явное создание (`BossGroup`, по одной активной группе на
  пользователя в неделю) + приглашение друзей (из списка уже принятых
  `Friend`) + принятие приглашения (`BossGroupMember`). HP = 300 × участников
  — при каждом новом участнике `hp_total` и `hp_remaining` увеличиваются на
  300 (а не пересчитываются с нуля), чтобы вступление в разгар недели не
  делало бой несправедливо тяжелее уже внесённого урона.
- Урон = XP (`base_points`), который дало бы ЭТО начисление (с учётом
  "пробуждения" и т.п.) — ровно то значение, что идёт в XP игрока. Урон
  наносят только отметки `done`/`minimal` (не `skip`) по привычкам
  участника, пока его группа активна на этой неделе (пн-вс, `_week_key`).
  Урон от КАЖДОЙ отметки обязательно логируется в `BossHit` — лента ударов.
- Победа (HP ≤ 0 до конца недели, пн-вс): каждому участнику — монеты (30,
  без trust/harmony множителей, как фиксированная награда за командную
  победу) + сундук (через ту же весовую систему редкости из п.9). Не
  добили за неделю — группа помечается `expired`, никакого штрафа никому.
- Чтобы не плодить отдельную таблицу избыточно: `Chest.habit_id` стал
  необязательным (`Optional[int]`) — награда за босса не привязана к
  привычке, но хранится в той же таблице `chests` для единообразия истории
  наград пользователя.

## 11. Достижения бронза/серебро/золото

- `Achievement` получил поля `category` (streak/sphere/honesty/boss/goals/
  comeback/personas) и `tier` (bronze/silver/gold, либо `None` для
  одиночных ачивок типа "все личности на стадии 5"). Код остаётся
  уникальным текстовым id (`streak_bronze`, `streak_silver`, ...) — так
  работает уже существующий механизм выдачи/проверки "уже есть" без
  переписывания его логики.
- "Честность": считается число СВОИХ отметок (`HabitHistory`, kind
  done/minimal), у которых есть хотя бы одно `HabitConfirmation` со
  статусом `confirmed` — то есть реально подтверждённые другом, не просто
  с фото. Пороги 25/100/300.
- "Сфера": любая из 5 личностей достигла уровня 5/10/20 (`sphere_level`,
  существующая функция) — проверяется по МАКСИМАЛЬНОМУ уровню среди всех
  5 сфер (достаточно одной "прокачанной" личности, не всех сразу — это
  отдельно покрыто одиночной ачивкой "все личности 5-й стадии").
- "Боссы": число побеждённых `BossGroup` (`status == "won"`), в которых
  пользователь был участником — 1/5/20.
- "Возвращения" ("comeback"): отметка (`done`/`minimal`) по привычке в
  день, где за ПРЕДЫДУЩИЙ календарный день по этой же привычке не было
  вообще никакой отметки (пропуск без заморозки/skip) — считаем такие
  "возвраты после пропуска" по всем привычкам пользователя, пороги 1/5/15.
- Монеты за тир: bronze 20 / silver 50 / gold 100 — так же, как в v6a
  (`coins_for_achievement`), только теперь берётся из `tier`, а не из
  зашитого вручную словаря по каждому новому коду.

## 12. Совет недели

- Доступен с 10-го уровня героя, показывается по воскресеньям
  (`today_for(user).weekday() == 6`) на `/hero`. Генерируется один раз за
  неделю (`week_key`) — хранится в новой таблице `WeeklyCouncilMessage`
  (а не в `CoachMessage`, чтобы не путать с обычной перепиской коуча;
  это отдельная "сцена", а не диалог).
- 5 реплик — по одной от каждой личности, о "прошедшей неделе" в целом
  (streak/XP/достижения за неделю для сферы этой личности) — заготовки
  в `persona_voices.py` (меньше вариантов на личность, чем у
  приветствия/пропуска/серии — это разовое событие раз в неделю, а не
  ежедневный текст, глубокая вариативность менее важна).

## 13. Сезон

- Один активный сезон одновременно (`Season`, 4 недели от `start_date`).
  Прогресс трека считается ЖИВЫМ запросом — сумма XP (`PointsLog.points`,
  без фильтра по сфере) с `time >= Season.start_date` до `end_date`,
  делённая на `XP_PER_SEASON_STEP` (40) и ограниченная 30 ступенями — без
  отдельного поля "прогресс", чтобы не хранить дублирующее состояние.
- "Бесплатный" трек — буквально: не требует монет/покупки, просто копится
  от обычной игры. Награды за ступени — таблица в коде (`SEASON_TRACK`,
  как `CATALOG` в `shop.py`), не в БД: более простая ступени 1-29 — монеты
  понемногу растут; каждая 5-я ступень (5/10/15/20/25/30) — сезонный
  предмет (`ShopItem.season_code` = код сезона, `price = None` — не
  продаётся, только через трек, визуально отличается от легендарных
  пометкой "сезонный" вместо "недоступен").
- Выдача по ступеням не повторяется — `SeasonClaim(uid, season_id, step)`
  уникален, проверяется и создаётся при каждом пересечении новой ступени
  (на /hero и после начисления XP) — ровно так же, как ачивки проверяются
  "уже получено?" перед выдачей.

# v6c — 3D-арт героя и личностей

## 14. Нарезка спрайт-листов

- `scripts/process_art.py` — разовый (но воспроизводимый, можно перезапустить
  при новых листах) конвейер: лист 1536×1024 → 5 кадров WebP на каждую
  стадию. Запуск без аргументов берёт `art_sources/` и пишет в
  `app/static/game/`.
- **Поиск границ между фигурами** — не деление на 5 равных частей, а
  минимум "профиля детализации" (сумма градиента яркости по столбцу) в
  окне вокруг каждой из 4 ожидаемых точек деления. Фон/свечение —
  гладкие (низкий градиент), силуэт персонажа — высокая детализация
  (складки, контуры, переходы цвета). Это работает даже там, где само
  свечение соседних фигур визуально соприкасается (как на поздних
  стадиях героя) — в отличие от порога по альфе/яркости, детализация не
  зависит от того, насколько ярким или тёмным оказался фон в этом месте.
- **Удаление фона** — свой алгоритм (не rembg, в окружении не было
  интернета для загрузки модели U2Net): difference matting от белого с
  порогом (`SOLID_THRESHOLD=195`) — пиксели, явно отличающиеся от белого,
  остаются ПОЛНОСТЬЮ непрозрачными (не тускнеют), плавный край появляется
  только в узкой переходной зоне (195–255) к чистому фону. Затем "размикс"
  цвета в этой зоне убирает белую примесь (`fg = (observed - (1-a)·255) / a`)
  — без этого полупрозрачные пиксели свечения сохраняли бы белый оттенок и
  давали заметный белый ореол на тёмном фоне приложения.
  Дополнительно: реальный белый фон источников оказался не 255,255,255,
  а ~253–254 (артефакт кодирования) — без явного среза шумового пола
  (alpha < 16 → 0) это давало равномерную, едва заметную, но СПЛОШНУЮ
  полупрозрачность по всему кадру, видимую как прямоугольный "бокс" вокруг
  фигуры на тёмном фоне. Файл героя уже был с альфой (бэкграунд-слой
  сделан заранее) — для него удаление фона не применяется, только
  нарезка по тому же профилю детализации.
- **Масштаб и холст** — один коэффициент на весь лист: берётся минимальный
  масштаб, при котором КАЖДАЯ из 5 тесно обрезанных фигур (bbox по альфе
  с запасом 18px на фактическое затухание свечения) помещается в холст
  480×480 с полями 22px — рост персонажа между стадиями остаётся частью
  дизайна, не нормализуется. Низ всех 5 фигур выровнен по одной линии
  (paste_y = CANVAS - MARGIN - height), по центру по горизонтали.
- Запасной файл мага ("Пять ступеней мудрости мага (1).png") сохранён в
  `art_sources/`, но не нарезается — альтернативный вариант на будущее.

## 15. Показ и вес страницы

- `game_asset_url()` ищет `.webp`, затем `.png`, иначе отдаёт прежнюю
  SVG-заглушку (`/game-placeholder/...`) — питомцы/боссы/рамки/фоны/
  бейджи пока без реального арта, ничего не меняется для них.
- Состояние личности — CSS-фильтр на `<img>`, не на карточке целиком
  (чтобы не тускнел текст): `.persona-img-dormant` (opacity 0.55) для
  "дремлет", `.persona-img-asleep` (grayscale+затемнение) для "спит".
  Ведущая личность — `.persona-card-leading` на карточке (box-shadow
  акцентным цветом, а не на изображении) — свечение карточки, а не фильтр.
- Все изображения героя/личностей/питомца — `loading="lazy"`.
- Фактический вес `/hero` с демо-данными — ~1.15 МБ (из них сам арт —
  ~80–100 КБ на 6 изображений; основной вес — внешние CDN-библиотеки
  Tailwind/Lucide/HTMX, которые грузились бы в любом случае).

# v6d — админ-панель

## 16. Доступ

- `ADMIN_LOGINS` читается на каждый запрос (`os.getenv`, без кеша) — так
  смена переменной на Render подхватывается при следующем деплое/рестарте
  без доп. кода. Пусто/не задано → админов нет вообще (ни один логин не
  совпадёт с пустым множеством) — безопасный дефолт.
- 404, а не 403/редирект на логин — чтобы не выдавать не-админу сам факт
  существования `/admin` (как и просили буквально).
- `is_admin` добавлен в контекст КАЖДОГО рендера через `app/rendering.py`
  (там же, где уже собирается XP-бар) — чтобы пункт меню "Админка" не
  требовал правки всех ~20 роутеров по отдельности.

## 17. Галерея — что считается "нужен арт"

- У титулов и эффектов отметки никогда не было концепции картинки (с v6a
  они всегда текстовые — титул рядом с ником, эффект как описание) — в
  галерее они показываются как текстовый образец, не как "заглушка",
  и не входят в счётчик "готово N из M" (нечего рисовать).
- У боссов нет собственной "силы"/сложности в реализации (один общий
  босс на неделю, без тиров) — в карточке показывается только название,
  без придуманного атрибута.
- "Готово" для стадии = реальный файл есть на диске по пути, который уже
  строит `game_asset_url()` (`.webp` или `.png`) — та же проверка, что и
  в рантайме, чтобы галерея не расходилась с тем, что увидит игрок.

## 18. Песочница — что именно переключают контролы

- Уровень героя: `Level.point` выставляется в кумулятивный XP-порог этого
  уровня (`sum(xp_for_level(l) for l in 1..level-1)`) — ровно та же
  формула, что считает текущий уровень, так что "ур. 20" в песочнице и
  "ур. 20" в реальной игре — одно и то же число.
- Уровень сферы: вместо добавления новой записи — все `PointsLog` этой
  сферы пользователя удаляются и заменяются ОДНОЙ строкой с нужным XP
  (`(level-1)*50`). Эта же строка задаёт и "состояние" личности (активна/
  дремлет/спит) — её `time` выставляется на 0 / 10 / 25 дней назад
  соответственно: `days_since_last_activity` берёт именно самую свежую
  запись, так что одна запись управляет и уровнем, и состоянием сразу,
  без противоречий между двумя контролами.
- Серия дней: привязана к отдельной скрытой привычке `_sandbox_streak`
  (создаётся по требованию, не показывается в обычном списке привычек —
  фильтруется по имени) — так серию можно двигать независимо от реальных
  привычек пользователя, не трогая их историю.
- Питомец: поля `species`/`best_stage_reached` выставляются напрямую,
  минуя проверку уровня героя (`hatch_pet`) — песочница имитирует
  результат, а не весь путь к нему.
- "Выдать всё" (предметы/достижения) — не идёт через обычные проверки
  условий, просто создаёт недостающие `InventoryItem`/`UserAchievement`.
  Монеты за это НЕ начисляются (в отличие от настоящей выдачи достижений)
  — это чит для осмотра контента, а не часть экономики.
- Сундук нужной редкости — `grant_chest()` получил необязательный
  параметр `forced_rarity`, который просто пропускает `roll_chest_rarity()`.
- Совет недели по кнопке — отдельная функция без проверки
  "воскресенье и ур.10+" (та же запись в `WeeklyCouncilMessage`, что и
  обычная генерация, только без гейта).
- Снимок для отката: JSON-строка в `SandboxSnapshot` (один на
  пользователя, первая правка создаёт — повторные не перезаписывают).
  Хранит только то, чем управляют контролы (XP героя, XP по сферам,
  монеты, trust, питомец) — купленные "выдать всё" предметы/достижения
  НЕ входят в снимок и не отменяются сбросом: они трактуются как
  необратимый чит на осмотр контента, а не временное состояние для теста.

## 19. Изоляция тестовых аккаунтов

- `User.is_test` выставляется в True при ЛЮБОЙ правке через sandbox
  (не только пресетами) — один раз выставленный, флаг не снимается
  сбросом к реальному прогрессу (сам факт, что аккаунт побывал в
  песочнице, не отменяем, только числа).
- Рейтинг друзей (`_friends_context`) и список групп для присоединения к
  боссу недели (`joinable_groups_for_user`) фильтруют `is_test` — тестовый
  аккаунт не портит прогресс-метрики реальных друзей и не затягивает их
  в бой с "ненастоящим" HP-пулом.
- Подтверждения друзей: тестовый аккаунт не может ни подтверждать чужие
  отметки, ни чтобы ему подтверждали — простая проверка `is_test` в
  начале обоих маршрутов `/confirmations/*`.
